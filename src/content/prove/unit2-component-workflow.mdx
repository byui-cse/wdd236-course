## Overview

In this assignment you will implement one critical workflow from your Unit 1 project proposal using at least one reusable native web component.

This prove has two expectations:

1. Consolidate your best planning and design decisions from Unit 2 prepare and ponder.
2. Extend that work into a complete implementation package with test evidence and component documentation.

## Objectives

- Implement a meaningful workflow using reusable web component boundaries
- Define and document a clear public API for your component
- Demonstrate test evidence for behavior, events, and accessibility
- Communicate tradeoffs and risks in a concise engineering summary

## **01** Workflow and Component Scope

Select one critical workflow from your Unit 1 proposal and identify:

1. Workflow goal and success state
2. One primary component responsible for key interaction behavior
3. What is in scope for Unit 2 implementation
4. What is explicitly out of scope for Unit 2

## **02** Implementation Requirements

Implement the workflow with at least one reusable native web component.

Minimum implementation requirements:

1. Component contract:
   - Attributes/properties
   - Events/custom events
   - Slots (if used)
2. Workflow coverage:
   - Normal path
   - One alternate or error path
3. Accessibility:
   - Include labels/instructions and user feedback for the implemented flow

## **03** Synthesis and Extension Requirements

Your submission should not just repeat your weekly notes. Revise and expand them.

Minimum extension requirements:

1. Finalize the component contract and boundaries based on implementation lessons.
2. Update your workflow map to reflect actual component/page responsibilities.
3. Expand your test plan into executed evidence.
4. Include one scope decision you intentionally kept out of implementation and why.

Provide test evidence for at least:

1. Three behavior checks
2. One event contract check
3. One accessibility check

For accessibility evidence, include at least one of the following:

1. Keyboard interaction behavior
2. Labeling/screen-reader support
3. Error feedback behavior

## **04** Evidence Package

Submit the following evidence:

1. Link to implementation code (or zipped source if instructed)
2. Short API documentation for the component:
   - Attributes/properties
   - Events/custom events and payload shape
   - Slots (if used)
   - In-scope vs out-of-scope responsibilities
3. Test evidence (screenshots, logs, test output, or checklist with proof)
4. One short reflection covering:
   - Two design decisions
   - One tradeoff
   - One unresolved risk

## **05** Unit Timeline and Milestones

This prove is due at the end of Unit 2 and should reflect learning from both weeks.

Week 3 milestone:

1. Candidate components identified
2. Primary component selected
3. Draft component contract and boundaries created

Week 4 milestone:

1. Workflow integration plan completed
2. Test plan finalized
3. Accessibility behavior expectations finalized
4. Evidence package prepared

## **06** Rubric

| Criteria | Exceeds | Meets | Needs Revision |
| --- | --- | --- | --- |
| Workflow Scope and Alignment | Scope is clear, realistic, and strongly aligned to Unit 1 workflow goals with explicit in/out boundaries. | Workflow scope, success state, and in/out boundaries are present and understandable. | Scope is vague, too broad, or disconnected from Unit 1 workflow intent. |
| Component API and Boundaries | API is clear, stable, and well-documented with strong boundary decisions and rationale. | API and boundaries are documented and mostly coherent for team use. | API or boundaries are ambiguous, inconsistent, or incomplete. |
| Implementation Quality | Workflow handles normal and alternate/error paths cleanly with reusable component design. | Workflow and component work for required paths with acceptable structure. | Required paths are incomplete or component integration is unstable. |
| Testing and Accessibility Evidence | Evidence is strong, specific, and demonstrates behavior, event contract, and accessibility quality. | Required evidence exists for behavior, events, and accessibility checks. | Evidence is missing, weak, or does not validate required checks. |
| Reflection and Tradeoffs | Reflection is concise and insightful with realistic risk analysis and next steps. | Reflection includes required decisions, tradeoff, and risk with reasonable clarity. | Reflection is missing required elements or lacks substantive analysis. |
